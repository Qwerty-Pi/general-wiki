Entity-Relationship (ER) Model

We will take the axiomatic approach: Every operation not explicitly said cannot be performed.

I. Attribute

Let's say the domain of the data is $D$ where $\texttt{null} \in D$. There are a few kinds of attributes:

Simple/Atomic$e \in D$.
Multi-valued$e \in 2^{D}$.
CompositeSuppose children with domain $D_1, \dots, D_K$. Then $e \in D_1 \times \cdots \times D_K$.
DerivedCan be computed from the rest attributes.

II. Entity

Entity consists of several attributes. If the attributes are with domain $D_1, \dots, D_K$, the domain of the entity is $D := D_1 \times \cdots \times D_K$.

Every entity must have a (set of) primary key, a chosen candidate key or minimal super key. A set of attributes $S$ is super key iff for every valid $E \subset D$ we have the cardinary of $E$ and $E|_{S}$ equal. Clearly $[K]$ is a super key and so candidate key exists.

Say the current entity is $\texttt{W}$. If some attributes is "borrowed" from another strong entity $\texttt{S}$, then Entity $\texttt{W}$ is weak, and its partial key is the set of non-borrowed attributes in primary key. Entity $\texttt{W}$ is linked to Entity $\texttt{S}$ via an Identifying Relationship.

III. Relationship

Relationship consists of several (at least 2) entity and several attributes. Its domain is (obviously) also the cartesian product.

We can impose constraints on relationship: Either cardinality or participation.

A. Cardinality Constraints

Three kinds of cardinality constraints: many-to-many, many-to-one and one-to-one. For relationship $R = E_1 \times E_2$, if for every valid $S \subset R$ we have cardinality of $R|_{E_k}$ = cardinality of $R$, then we can deduce $R$ uniquely from $E_k$ alone.

B. Participation Constraints

Two kinds of participation constraints: total and partial. For relationship $R = E_1 \times E_2$, the participation of $E_k$ is total iff for every valid $S \subset R$ we have $S|_{E_k} = E_k$.

IV. Other Notations

Aggregation: For relationship between relationship and/or entity.

ISA: For class hierachy.

Relational Model

(Side Note: Notation are non-standard. But why there isn't notation for schema and instances?)

Relation $\mathcal{R} = (\Sigma, S)$ consists of relational schema $\Sigma$ and relational instances $S$.

Relational Schema $\Sigma$ is an ordered tuple of pairs: $\{ (A_1, D_1), \dots, (A_K, D_K) \}$, where $A_i$ and $D_i$ are the name and domain of the $i$-th attribute, respectively.

Relational Instances $S$ is a subset of $D_1 \times \cdots \times D_K$, representing all the possible relations.

We can define Primary Key (PK) in relation as well - similar to that in ER Model. A Foreign Key (FK) is a "pointer" to another relation with its Primary Key (PK).

Integrity Constraints is what we want the data to satisfy. Three major kinds of integrity constraints are

  1. Key Constraint - PK must be unique
  2. Entity Integrity - PK cannot contains $\texttt{null}$, and
  3. Referential Integrity - FK either $\texttt{null}$ or exists

To convert from ER Model to Relational Model, simply use common sense to decide what primary key to choose in relation.

Relational Algebra

Relational Algebra can be considered as a language on relations, and based on set theory. The notations are as follows:

  1. (Select) $\sigma_{P}(\mathcal{R})$ returns a relation with the same schema as $\mathcal{R}$ and rows that satisfy the selection predicate $P$.
  2. (Project) $\Pi_{S}(\mathcal{R})$ returns a relation with schema $S$ and the projection of $\mathcal{R}$ onto $S$.
  3. (Rename) $\rho_{\mathcal{S}(A_1, \dots, A_K)}(\mathcal{R})$ returns the original $\mathcal{R}$ but renamed (with or without columns).
  4. (Join) $\mathcal{R} \bowtie_{P} \mathcal{S}$ returns $\sigma_P(\mathcal{R} \times \mathcal{S})$. If $P$ is omitted, it is natural join and all attributes appear in both $\mathcal{R}$ and $\mathcal{S}$ are equi-joined.
  5. (Division) $\mathcal{R} / \mathcal{S}$ returns a relation with schema $S_\mathcal{R} \setminus S_\mathcal{S}$ and instances $\{ x \in D_\mathcal{S} / D_\mathcal{R} \, | \, \{x\} \times \mathcal{S} \subset \mathcal{R} \}$.

Structual Query Language (SQL)

Functional Dependencies (FD)

Functional Dependency: $\alpha \rightarrow \beta$ is defined to be $r_1[\alpha] = r_2[\alpha] \implies r_1[\alpha] = r_2[\beta]$ for all $r_1, r_2 \in S$ over all legal extensions $S$.

Armstrong's Axiom For $\alpha, \beta \subset \Sigma$, we have

  1. (Reflexivity) $\beta \subset \alpha \mid= \alpha \rightarrow \beta$.
  2. (Augmentation) $\alpha \rightarrow \beta \mid= \alpha \gamma \rightarrow \beta \gamma$.
  3. (Transitivity) $\{ \alpha \rightarrow \beta, \beta \rightarrow \gamma \} \mid= \alpha \rightarrow \gamma$.

Closure $F^+$ of functional dependencies $F$ is defined to be the set of all functional dependencies that can be inferred from $F$.

Closure $\alpha^+$ for $\alpha \subset \Sigma$ is defined similarly. $\alpha$ is super key of $\mathcal{R}$ iff $\alpha^+ = \Sigma$.

Relation Decomposition

A relation $\mathcal{R} = (\Sigma, S)$ can be decomposed to $\mathcal{R_k} = (\Sigma_k, S_k)$ where $\Sigma = \cup_k \Sigma_k$ and $S_k = \Pi_{\Sigma_k}(S)$.

A decomposition is lossless-join if $S = S_1 \bowtie \cdots \bowtie S_K$ for all $S$. For $K = 2$, equivalently, $\Sigma_1 \cap \Sigma_2 \rightarrow \Sigma_k \in F^+$ for at least one $k$.

Dependency is preserved iff $(F_1 \cup F_2)^+ = F^+$ where $F_k = F^+|_{\Sigma_k}$.
