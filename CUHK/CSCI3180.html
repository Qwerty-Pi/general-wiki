CSCI3180 Principles of Programming Languages

Introduction

Consider a program in language $\mathcal{L}$. We care about mainly two things: (1) Syntax (definition of set $\mathcal{L}$) and Semantic (how the program in $\mathcal{L}$ does). Mathematically, we can treat interpreter as a partial function that maps from the language to values: $$\text{Interpreter}_{\mathcal{L}} : \mathcal{L} \rightharpoonup \mathcal{V}$$

Whereas compiler is a function between two languages where $$ \text{Interpreter}_{\mathcal{L}_1} = \text{Interpreter}_{\mathcal{L}_2} \circ \text{Compiler}_{\mathcal{L}_1 \rightarrow \mathcal{L}_2}$$

Sometimes we create syntactic sugar, for instance (not e) === (if e then true else false). We can denote this relation as $$ \text{Evaluator}_{\mathcal{L}} = \text{Evaluator}_{\mathcal{L}_\text{core}} \circ \text{Desugarer}_{\mathcal{L}} $$

Target: Can we create an abstracted mathematical model for programs?

Syntax and Formal Language

Backus-Naur Form (BNF) is a way for us to specify the grammar of a language. An example for boolean is t ::= true | false | t and t | t or t, where t is called metavariables (to distinguish with actual variables). Given such a grammar, we can create the parse tree of any syntactically valid term, which is the Abstract Syntax Tree (AST), and can be translated to Abstract Data Type (ADT) in programming languages.

We can define potentials on ASTs such as constants, size and depth, and carry out Structural Induction on AST (simply because it is a rooted tree). Well-founded relation are partial order such that there does not exists infinite descending chain, which we can induct on it.

Simply refer to CSCI3130 Notes for more details.

Semantics

There are three styles of discussing semantics, as listed as follows:

  1. Operational Semantics: context |- term -> (new term, new context)
  2. Denotational Semantics: [[term]] := context -> value
  3. Axiomatic Semantics: (Hoare triple) {predicate P} program {predicate Q}

Each of them are slightly different, but yet the main idea is the same: to find out the axiomatic inference rules for basic programming blocks (boolean, if-then-else, while-loop, etc), and use them to apply on everything.

Abstract Rewriting System over language $\mathcal{L}$ is a relation $\mathcal{R}$ over $\mathcal{L} \times \mathcal{L}$ where we can replace $x \in \mathcal{L}$ by $y$ iff $(x, y) \in \mathcal{R}$, which is called (small-step) reduction, and is denoted as $x \rightarrow y$. We denote its transitive closure, (big-step) evaluation, as $x \Downarrow y$. A Proof System is a special case where we derive truth ($\top$) and false ($\bot$).

We call $(\mathcal{L}, \rightarrow)$ is confluent iff $w \Downarrow x \land w \Downarrow y \implies x \Downarrow z \land y \Downarrow z$ for some $z \in \mathcal{L}$, which is exactly when the evaluated result is deterministic (the actual evaluation is not required to be deterministic). Meanwhile, we call $\rightarrow$ as terminating if for all $x \in \mathcal{L}$, any reduction chain is finite.

We define $x \in \mathcal{L}$ to be in normal form iff $x$ cannot be further reduced, while we usually also denote a subset of normal form as values which is the set of expected results. Non-value normal form indicates the program has gotten stuck and runtime-error has occured.

Untyped Imperative Language

There are two main components: The syntactic form (syntax) and evaluation rules (semantics). First, arithmetics:

Booleans $\mathbb{B}$

Syntactic Forms
  • Terms t ::= true | false | if t then t else t
  • Values v ::= true | false
Evaluation Rules
  • if true then t2 else t3 -> t2
  • if false then t2 else t3 -> t3
  • t1 -> t1' => if t1 then t2 else t3 -> if t1' then t2 else t3

Natural Numbers $\mathbb{N}$

Syntactic Forms
  • Terms t ::= 0 | succ t | pred t | iszero t
  • Values v ::= nv
  • Numeric Values nv ::= 0 | succ nv

The evaluation rules are just common senses so I omit them. The above are in the style of small-step operational semantics.

Simple Imperative Language (SIMPL)

Syntactic Forms
  • Terms t ::= v | skip | r := t (assignment) | !r (deference) | t1; t2 (sequence) | if t1 then t2 else t3 | while t1 do t2 | t1 op t2
  • Operators op ::= + | - | * | / | <=
  • Values v ::= b: bool | z: int

Common sense prevails. One may deduce the evaluation rules in both small-step and big-step operation semantics.

Functions

Idea: can we encode functions as objects? Turns out we can!

Lambda Calculus (λ)

Syntactic Forms
  • Terms t ::= x | λx. t (abstraction) | t1 t2 (application)
  • Values v ::= x | λx. t
Evaluation Rules
  • t1 -> t1' => t1 t2 -> t1' t2
  • t2 -> t2' => t1 t2 -> t1 t2'
  • (λx. t) v -> [x |-> v] t or t[v/x]

The binder λx has its scope extends rightwards. A variable $x$ is bounded if it is in scope of some λx, and free otherwise. A λ-term without free variables is called closed and is a combinator. It is possible to have nameless version of λ-Calculus by replacing variable names with integers. Capture-avoiding Substitution is always done, which simply means when substitution we avoid captures to not change the meaning.

A term of the form (λx. t) v is called a redex (reducible expression). There are different evaluation strategies: (1) beta-reduction: reduce everything (Church-Rosser Theorem states that this is confluent); (2) call-by-name: only reduce term outside abstraction, and from out to in; (3) call-by-value: only reduce term outside abstraction, and from in to out; (4) call-by-need: only lazily call when needed by using thunks, which abstracts the function to a value in a call-by-value scenario, whereas memorisation can also be done. Infinite lazy list can be defined as well.

The Church Encoding allows us to express everything in λ-Calculus:

Church Boolean
  • tru = λt. λf. t (true)
  • fls = λt. λf. f (false)
  • test = λl. λm. λn. l m n (if-then-else)
Church Pair
  • pair = λf. λs. λb. b f s
  • fst = λp. p tru
  • snd = λp. p fls
Church Numeral
  • c0 = λs. λz. z
  • cn = λs. λz. sn(z)
  • scc = λn. λs. λz. s (n s z)

Simple Abstract Machine Language (SAML)

Syntactic Forms
  • Terms t ::= id | if t1 then t2 else t3 | fun args -> t | t1 t2 | let bind in t | op t | t1 binop t2 | let rec x = fun x -> t in t
  • Bindings bind ::= x = e | x = e, bind
  • Identifiers id ::= x | z | b
  • Arguments args ::= x | x args
  • Binary Operators binop ::= + | - | * | / | and | or | <=
  • Unitary Operator op ::= not
  • Values v ::= z | b | fun args -> t

For a matter of fact, some of the above -> are actually partial functions, but one may just interpret them using common sense.

Recursion

How to define recursions? In fact, for f: X -> Y we can define F : (X -> Y) -> X -> Y that maps f to f'. By fix f = λf. (λx. f(λy. x x y)) (λx. f(λy. x x y)), we have fix F = F(fix F) a fixed point of F, which is computes the result of the recursion given that it terminates.

Scoping

There are two major types of scoping: (1) Lexical (Static) scoping, which the scope is deduced from syntax; (2) Dynamic Scoping, which the scope is deduced from semantics, e.g., OCaml is static scoping. In many languages, there are also global scope and local scope, and we can alias variables.

With (mutable) environment (in constract with immutable context), we can no longer treat functions as first-class, and we need to treat function along the environment as a closure.
