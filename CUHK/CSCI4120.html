Rendering and Display

A raster graphics is a 2D rectangular grid of pixels in some colour spaces. The screen is rendered in a raster pattern, each row from left to right and from top to bottom, where VBLANK is time from bottom right to top left. Refresh rate is the max number redrawn of the screen per seconds, where frame rate refers to the actual number of frames drawn of the game per second.

We use a framebuffer in the RAM to store the computed image. If done incorrectly, we may have screen tearing (partly old frame and partly new frame) or screen flickering (objects suddenly appear and disappear) since a frame can be partially drawn. We may utilise multiple buffers (double / triple buffering) and V-sync (force buffer swap in VBLANK) to resolve the issues. Variable refresh rate (VRR) let monitor to dynamically refresh, allow a lower input latency.

Game Engines

Game libraries are low-level toolkit for specific domains, game frameworks provide reusable components and patterns, whereas game engines are complete suite for all core systems of a game. Game engines allow efficient work division, rapid development, asset reusability and cross-platform support. However, it also leads to homogenisation of games, creativity constraints, performance overhead and licensing cost.

All real-time game based on a game loop, where the input is continuously processed, update the game and render the frame. HUD (heads-up display) refers to the information directly shown such as health bars. Sometimes we want fixed timestamp so that it is deterministic, but it might also lead to visual stutter and performance bottlenecks. We may also use a variable timestamp and use time delta instead. We have smoother visuals but the physics might be inconsistent or missing collision. The modern game engine usually adapt a hybrid approach and supports both.

2D Graphics

A sprite is a 2D image or animation for a visual object. We convert them from standard image formats to GPU-native formats such as BC7 and ASTC, which uses hardware texture compression to reduce VRAM usage and communication overhead. A sprite sheet (teture atlas) is a image file containing many smaller sprites in a grid, which reduce number of I/O calls and enable better caching and animation. A similar concept is the tilemap where each tile is a small reusable image.

A texture is an image we map to objects with UV coordinates. We can wrap the texture (repeat, mirror, clamp-to-edge, clamp-to-border) when UV coordinates go out of 0.0 to 1.0. Meanwhile, in 2D games, we often support different kind of scrolling, including horizontal, vertical, omnidirectional and parallax.

To render 2D objects, we may use painter's algorithm which we render background then foreground elements. The dirty rectangle method optimises this by only redrawing the changed area. Anti-aliasing might be necessarily to prevent jagged lines, which includes supersample (SSAA), multisample (MSAA), fast approximate (FXAA) and subpixel morphological (SMAA).

3D Graphics

In game, we have the graphics primitives including points, lines and polygons, where a mesh represents the surface of a 3D object. We usually use triangle meshes via triangulation, which is stored with vertex data and index data.

For coordinate systems, we have model coordinates, world coordinates, view coordinates (camera), clip coordinates (after projection), normalised device coordinates (NDC) (3D, -1 to +1) and viewport coordiantes (2D). Two main kinds of projections include perspective projection and orthographic projection. Rasterisation involves the top-left rule, where fragments are produced. Depth test and stencil test are done before writting to framebuffer. For depth test, we use Z-buffer nowadays, where forward-Z (uniform) and reverse-Z (reversed floating-point) to avoid clustering at near plane.

Lighting

To produce lighting, we consider different light sources such as point light, directional light, spotlight and ambient light. Different lighting and reflection models are used to simulate physical lighting. The simplest model is the Phong Illumination Model, which includes ambient, diffuse and specular components.

Physical-Based Rendering (PBR) is a more advanced technique to approximate light-surface interactions, which attempts to conserve energy and use physically meaningful parameters. At core, we use the bidrectional reflectance distribution function (BRDF), which includes diffuse and specular components. In PBR, we can use texture to affect the lighting. In the metallic-roughness workflow, parameters include albedo (base colour), normal, roughness, ambient occlusion (visibility), metallic, height (bump), alpha and emissive maps. Another PBR workflow is the specular-glossiness workflow, where one can change the diffuse, specular and glossiness map directly.

Shadow

We need shadow. How to create shadow? The simplest way is via shadow volume, which we cast light rays from the light sources to the objects to create hard shadows by marking them to stencil buffer. A better way is via shadow mapping, which we carry out a two-pass rendering by rendering at the light source first to produce the shadow (depth) map, then re-render at camera.

To create soft shadows (umbra / penumbra), one may use Percentage Closer Filtering (PCF) which averages the shadow over a small kernel (3x3). The Percentage Closer Soft Shadows estimate the penumbra width and use that as parameter for PCF. Aritfacts of shadow mapping include shadow acne (shading itself), peter-panning (shadow detach from object), perspective aliasing (resolved via Cascaded Shadow Maps, CSM).

Finally, we can also cast rays from surface towards the light source. After hitting a surface, secondary rays (shadow, reflection, refraction, indirect-lighting) may be casted, where path tracing samples different directions and take averages.

Rendering

In forward rendering, lighting and shading are computed for all fragments, while in deferred rendering the geometry of the scene is stored and the surface data is stored in the G-buffer (geometry buffer) in the geometry pass, then in the lighting pass the G-buffer data is used to compute lighting. With G-buffer, many post-processing effects can be used, for instance depth of field, bloom (blur of bright pixels), Sceen Space Reflections (SSR)(approximate reflections) and Screen Space Ambient Occlusion (SSAO) (sample nearby depth for occlusion). To avoid a full deferred rendering, we have forward+ rendering which we do light culling per tile (16 x 16 pixels). Finally, environment mapping and lightmapping can be used.
